# Spec — Eval Framework

> Prompts are the real code. Evals are the tests for prompts. Without evals, every prompt change is a regression risk.

## Goal

Continuous evaluation of agent quality across:
- Memory recall accuracy
- Email triage correctness
- Meeting prep quality
- Decision support relevance
- Network suggestion value
- Voice latency + quality
- Cost per task

## Three tiers

### Unit evals (per prompt, per task)

- Run on every commit touching `packages/ai/prompts/` or `packages/ai/agents/`
- < 30 seconds
- Small fixtures (5-20 cases per prompt)
- Block PR if regression

### Integration evals (per agent flow)

- Run on PR
- 2-5 minutes
- End-to-end scenarios
- Block merge if regression

### Regression evals (full suite)

- Run nightly + before deploy
- 30+ minutes
- Full golden datasets (200+ cases)
- Block deploy if regression > tolerance

## Eval methods

### Deterministic comparison

For tasks with ground truth (e.g. memory recall: did we return the right memory ID?).

```typescript
test('memory recall — name lookup', async () => {
  const fixtures = loadFixtures('memory-recall');
  const recallScores = [];
  for (const f of fixtures) {
    const results = await memory.recall(f.query, { limit: 5 });
    const got = results.map(r => r.memory.id);
    const recall = computeRecallAtK(got, f.expected, 5);
    recallScores.push(recall);
  }
  const avgRecall = mean(recallScores);
  expect(avgRecall).toBeGreaterThanOrEqual(0.85);
});
```

### LLM-as-judge

For subjective quality (e.g. is this email draft good?).

```typescript
test('email draft quality', async () => {
  const fixtures = loadFixtures('email-draft');
  const scores = [];
  for (const f of fixtures) {
    const draft = await emailAgent.draftReply(f.email, f.userVoiceProfile);
    const judgement = await llmJudge({
      criteria: 'helpfulness',
      input: f.email,
      output: draft,
      rubric: HELPFULNESS_RUBRIC,
    });
    scores.push(judgement.score);  // 1-5
  }
  expect(mean(scores)).toBeGreaterThanOrEqual(4.0);
});
```

LLM judges:
- Use Claude Opus 4.7 (more capable, less variance than Sonnet)
- Always use structured output (zod schema for judge response)
- Always provide explicit rubric in prompt
- Run each judgement 3x and average (variance reduction)

### Pairwise preference

For comparing prompt variants (A/B).

```typescript
const a = await runWithPrompt('v1', cases);
const b = await runWithPrompt('v2', cases);
const wins = await pairwiseJudge(a, b);
// expect b > a if v2 is improvement
```

### Latency / cost

For performance budgets.

```typescript
test('email triage — latency p95', async () => {
  const latencies = await runEachAndMeasure(fixtures, emailAgent.triage);
  expect(p95(latencies)).toBeLessThan(2000);
});
```

## Datasets

Each dataset:
- Hand-curated initially (1-5 hours per dataset)
- Augmented with synthetic cases generated by Claude Opus
- Reviewed quarterly
- Versioned in git

Suggested initial sizes:
- memory-recall: 200 cases
- email-triage: 200 cases
- meeting-prep: 50 cases
- decision-support: 30 cases
- network-suggestions: 50 cases

## Metrics tracked

```typescript
type EvalRun = {
  id: string;
  date: Date;
  commit: string;
  suite: 'unit' | 'integration' | 'regression';
  results: {
    [taskName: string]: {
      metric: 'recall@5' | 'precision@5' | 'helpfulness' | 'latency_p95' | 'cost_per_task';
      value: number;
      baseline: number;
      delta: number;
      status: 'pass' | 'fail' | 'warn';
    }
  };
  totalCost: number;
  duration: number;
};
```

Saved to `eval/runs/<date>-<commit>.json`. Latest baseline at `eval/baseline.json`.

## Promotion rules

- **Block PR**: any unit eval regresses by > 5% absolute or fails hard threshold.
- **Block merge to main**: any integration eval regresses > 10%.
- **Block deploy to prod**: any regression eval regresses > 5%.
- **Update baseline**: only after manual review by founder. PR template includes "I have reviewed eval delta and accept it."

## Cost of running evals

- Unit: ~$0.50/run (cheap)
- Integration: ~$5/run
- Regression: ~$30/run (nightly, budgeted ~$1k/month)

Mitigations:
- Cache LLM responses by input hash → near zero cost re-runs
- Use Haiku for judge variance runs

## Eval tooling

```bash
pnpm eval                  # full unit + integration
pnpm eval:unit             # unit only
pnpm eval:regression       # full suite + baseline compare
pnpm eval:ai <prompt-path> # eval just one prompt
pnpm eval:diff <commit>    # compare to baseline at commit
```

## Eval-driven prompt iteration

When iterating on a prompt:

1. Run baseline: `pnpm eval:ai prompts/email/triage.v1.md` → save scores
2. Make a copy `triage.v2.md`, modify
3. Run new: `pnpm eval:ai prompts/email/triage.v2.md`
4. Compare. If v2 wins on metrics that matter, promote.
5. If mixed, pairwise judge with both.
6. Document promotion in DECISIONS.md as ADR.

## Failure investigation

When eval regresses:
1. Look at top 5 cases where score dropped most
2. Manually inspect inputs, outputs, judge reasoning
3. Hypothesize cause (prompt change, model behavior change, data drift)
4. Patch + re-run
5. If model behavior change: pin model version, file with vendor

## Continuous learning

Track in `eval/learnings.md`:
- "Adding 'be concise' to system prompt regressed helpfulness on long-form questions by 8%"
- "Switching from Sonnet to Haiku for email-triage saved 60% cost but regressed P0 detection by 12%"

Build institutional memory.
